# 技术架构与设计决策

> 这份文档的目标是让你在答辩时能**讲清楚每个"为什么"**，而不只是"它能跑"。

## 一、一句话定位

把业务人员的一句自然语言，变成 Flowable 引擎**能直接部署**的 BPMN 2.0 文件。

## 二、分层架构

```
┌─────────────────────────────────────────────────┐
│  S3 交互层（待做）                                 │
│  自然语言输入 → 提示词编排 → 结构化输出 → IR        │
└──────────────────────┬──────────────────────────┘
                       │ IR (JSON)
┌──────────────────────▼──────────────────────────┐
│  S2 修复层   repair.js                           │
│  只修确定性错误（id/自环/悬空端点/多余默认流）      │
│  不猜语义错误（悬挂、不可达、缺默认流）→ 交回上游    │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│  校验层（三道闸门，逐级放大成本）                   │

│  L3 graph.js    图论：起止唯一/悬挂/可达/死路/网关   │

└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│  序列化层  layout.js + serialize.js               │
│  最长路径分层排版 → DI 坐标 → BPMN XML（确定性）    │

                       │ BPMN 2.0 XML
┌──────────────────────▼──────────────────────────┐
```

## 三、五个关键设计决策（答辩必问）

### 决策 1：让模型产出 IR，而不是直接产出 XML

| | |
|---|---|
| **选了什么** | 大模型只输出 JSON（节点 + 连线），XML 由确定性代码生成 |
| **备选方案** | 直接让模型写 BPMN XML |
| **为什么否决备选** | 让模型写 XML，等于把 5 类随机故障同时引进系统：命名空间拼错、id 冲突、坐标缺失、标签未闭合、特殊字符未转义。而且**每次失败方式都不一样**，无法用测试覆盖。 |
| **代价** | 需要多写一层序列化器（约 200 行） |
| **收益** | 结构非法在物理上不可能发生；同一 IR 永远产出同一 XML（P-06） |

**这句话可以背下来**：*"我把'生成'这个不确定性挡在了 XML 之外，模型只负责语义，语法由代码负责。"*

### 决策 2：零运行时依赖

| | |
|---|---|
| **选了什么** | 校验、布局、序列化全部手写，不用任何 npm 包 |
| **备选方案** | 用 `bpmn-moddle` 做校验、用 `bpmn-auto-layout` 做排版 |
| **为什么否决** | 这两个包确实更成熟，但会引入 `node_modules`、版本锁定、供应链风险；比赛交付要求"完整可运行"，零依赖意味着克隆下来直接 `node` 就能跑，评审不会卡在 `npm install` 失败上 |
| **代价** | 自己的 XML lint 不如专业 XSD 严谨 |
| **补救** | 计划在 S4 把 `bpmn-moddle` 作为**可选依赖**引入做交叉验证，核心链路不依赖它 |

### 决策 3：选 Flowable 而不是 Camunda

| | |
|---|---|
| **选了什么** | Flowable 7（`xmlns:flowable="http://flowable.org/bpmn"`） |
| **为什么否决 Camunda 8** | Camunda 8 走 Zeebe + Elasticsearch + gRPC job worker，架构完全不同，本地跑起来要容器 + 内存，跟"不污染本机"的原则直接冲突 |
| **为什么否决 Camunda 7** | 也可以，但 Camunda 7 已进入维护末期；Flowable 开源活跃、嵌入式 H2 开箱即用 |
| **注意** | 两者方言不同：`flowable:assignee` vs `camunda:assignee`。选了就不能混 |

### 决策 4：必须自己算 DI 坐标

**这是最容易翻车的地方**。BPMN XML 分两半：`<bpmn:process>` 是逻辑，`<bpmndi:BPMNDiagram>` 是坐标。

只生成逻辑段 → 引擎能部署能跑 → **bpmn-js 打开一片空白** → 演示当场死。

所以 `layout.js` 用最长路径法分层（图层 = 从开始节点的最长距离），同层纵向排开，连线用正向直角折线、回边绕行。测试里断言 `Shape 数 == 节点数 && Edge 数 == 连线数`。

### 决策 5：修复只修"确定性错误"

| 可自动修 | 绝不自动修 |
|---|---|
| 缺 id | 缺 type（不知道该建成什么节点） |
| id 重复 | 悬挂节点（不知道该连到谁） |
| 自环连线 | 不可达节点（不知道该从哪连过来） |
| 端点不存在的连线 | 排他网关没默认流（不知道该默认走哪条） |
| 多余/非法的默认流 | 条件表达式写错（不猜业务语义） |

**理由**：帮用户"猜"一条线，看起来聪明，实际是在制造无法解释的流程。宁可报错让他改。

## 四、三个核心技术难点

### 难点 1：模型幻觉 → 图论非法

模型经常生成"看起来合理但跑不通"的图：三个结束事件、某个审批节点没有出口、排他网关所有分支都有条件但没有默认流。

**最后一类最阴险**：XML 完全合法、XSD 也通过、引擎也能部署，但**运行时所有条件都不满足，实例永久卡死**。

**解法**：`graph.js` 做静态可达性 + 死路分析，在进引擎之前就拦掉。

### 难点 2：条件表达式要懂，但不能执行

Flowable 用 JUEL 表达式（`${amount > 1000}`）。我们不求值，只做两件事：
1. 检查表达式里引用的变量是否已声明（防止 `amout` 拼错）；
2. 检查排他网关是否有默认流（防止卡死）。

**不求值的原因**：求值需要构造上下文、处理类型强转，容易误判；静态检查已经能覆盖主要风险。

### 难点 3：布局不能靠"感觉"

节点少的时候手写坐标没问题，节点一多必须算法化。选了最长路径分层（而不是力导向）：
- 力导向好看但**不确定**（每次结果不同，违反 P-06）；
- 分层布局**确定、可复现、符合人阅读审批流的从左到右直觉**。

## 五、可验证性设计（这是加分项）

| 手段 | 位置 | 作用 |
|---|---|---|
| 黄金用例 | `test/cases/` | 正向：必须全绿 |
| 反向用例 | `test/cases-bad/` | 坏图**必须**被拒绝，证明守卫不是摆设 |
| 可修复用例 | `test/cases-repairable/` | 脏 IR 修完必须合法、不修必须报错 |
| 原则检查 | `scripts/check-principles.js` | 9 条工程原则自动验证，红灯不得产出 |
| 独立交叉验证 | .NET XML 解析器 | 不用自己的 lint 给自己打分 |

## 六、可能的追问与回答

**Q：你这套跟直接调 bpmn-js 的建模器有什么区别？**
A：bpmn-js 是**人画图**，我们是**话变图**。而且我们生成的是完整 DI 的 XML，能直接喂给引擎，不是画完还要手工对齐。

**Q：模型理解错了怎么办？**
A：三道闸门会拦。但更重要的是——理解错通常表现为"图论非法"（比如漏了出口节点），这类错误位置明确、错误码结构化，可以定向重试而不是整段重生成。

**Q：为什么不用 LangChain 之类的框架？**
A：这个任务的编排只有 4 步（提示 → 解析 → 校验 → 序列化），引框架带来的抽象成本大于收益，而且会破坏零依赖原则。

**Q：怎么证明生成的 BPMN 真能跑？**
A：不能靠嘴说。S5 会用 Flowable 嵌入式引擎真实部署 + 跑实例 + 断言实际走过的节点序列，产出日志和报告。
